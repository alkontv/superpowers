# Форк Superpowers (alkontv)

Плагин ставится отсюда, а не из официального маркетплейса Anthropic и не напрямую от автора:

- официальный маркетплейс отстаёт: 08.10.2026 он держал 6.4.1, а у автора с 25.09.2026 была 6.4.2
  с переписанным `writing-plans` (план без полного кода);
- изменения автора попадают в форк только после просмотра; сам плагин обновляется из форка
  автоматически (`autoUpdate: true` у маркетплейса `alkontv-superpowers`), поэтому в `main` форка —
  только проверенное;
- скиллы можно править под себя, и при обновлении автора правки не теряются.

## Что изменено относительно оригинала

База — версия автора v7.0.0. Правки скиллов добавлены короткими вставками рядом с текстом автора, там,
где принимается решение.

- `.claude-plugin/marketplace.json`: имя маркетплейса `alkontv-superpowers` вместо `superpowers-dev`.
- Этот файл.
- Версия в `.claude-plugin/plugin.json` и `marketplace.json`: `7.0.0-alkontv.3` (формат
  `<версия автора>-alkontv.N`). Без своего суффикса Claude Code не видит правок форка при той же
  версии автора и не обновляет плагин; N растёт с каждой правкой форка, при переходе на новую
  версию автора — снова 1.
- `skills/test-driven-development/SKILL.md`: объём прогона набора тестов и пункт чек-листа «All tests
  pass» следуют политике проверок проекта, если она есть. Зачем: иначе скилл требовал полный набор
  на каждую задачу вопреки правилам проекта (тесты задачи, полный набор в конце ветки, очередь
  тяжёлых прогонов).
- `skills/verification-before-completion/SKILL.md`: записанное доказательство (коммит, команда,
  результат, окружение, лог) для той же ревизии считается свежим, если инструкции проекта его
  принимают. Зачем: иначе тяжёлый набор перегонялся перед «готово» на ревизии, у которой уже есть
  доказательство.
- `skills/subagent-driven-development/implementer-prompt.md`: если инструкции проекта задают другой
  объём проверок, исполнитель следует им и в отчёте называет непрогнанное. Зачем: исполнителю нельзя
  противоречить правилам проекта о полном наборе.
- `skills/using-git-worktrees/SKILL.md`: если инструкции пользователя оставляют детали исполнения
  агенту, рабочую копию и продолжение при падающих базовых тестах агент решает сам и докладывает.
  Зачем: исполнение утверждённого плана не должно ждать ответа на вопрос о рабочей копии.
- `skills/finishing-a-development-branch/SKILL.md`: если инструкции пользователя задают, как сдавать
  ветку, меню из трёх вариантов не показывается — сдать по правилам и доложить; удаление работы
  по-прежнему только по прямой просьбе. Полный набор проходит через механизм проекта (очередь или
  CI). Если итоговое ревью было самопроверкой, оставило открытые находки или правки после него не
  прошли ревью — ветка не сдаётся: технические находки исправляются, прогон Step 1 повторяется,
  новая ревизия идёт на независимое ревью, мелочи — в бэклог; пользователю — только настоящий
  блокер. Зачем: сессия не должна останавливаться на выборе, который пользователь уже сделал в
  своих правилах, и не должна сдавать непроверенное состояние.
- `skills/executing-plans/SKILL.md`: слияние, пуш и публикация не повод остановиться, если
  инструкции пользователя их уже разрешают (слияние PR на ревизии, одобренной итоговым ревью, после
  зелёных проверок); самопроверка автора не заменяет независимое ревью, если его требуют правила;
  при правиле «ревью каждой правки после ревью» вместо одного прохода правок — правки и независимое
  повторное ревью до чистого; объём прогона после правок и в таблице оправданий следует политике
  проверок проекта; файлы-доказательства переносятся из рабочей папки плана до её удаления;
  итоговый ревьюер запускается как `alkontv-dev:reviewer`, если такой тип агента есть, с моделью и
  усилием из таблицы моделей пользователя. Зачем: один проход без повторного ревью противоречил
  правилу «изменение после ревью — ревью нового состояния», а ссылки на доказательства в отчётах
  вели в удалённую папку.
- `skills/subagent-driven-development/SKILL.md`: то же про остановки, повторное ревью и перенос
  доказательств (журнал тоже доказательство); таблица моделей пользователя главнее «cheapest tier»:
  `model` и `effort` задаются явно на каждом запуске, итоговое ревью — по строке таблицы; исполнители
  и правки — `alkontv-dev:developer`, все ревьюеры — `alkontv-dev:reviewer`, если эти типы агентов
  есть; строки `Ruling:` из отчёта исполнителя копируются в журнал до закрытия задачи. Зачем:
  без таблицы запуск без модели наследовал самую дорогую, а решения исполнителей не доходили до
  итогового отчёта.
  Итоговое ревью ветки, где есть задачи `complex` или `high`, — два ревьюера параллельно: «корректность,
  требования, тесты» и «приватность, безопасность, потеря данных, договор с бэкендом»; ветка принята,
  только когда оба одобрили одну ревизию; повторное ревью после правок — тоже по срезу, по всему списку
  находок. Только для SDD, executing-plans не меняется. Зачем: больше охвата на рискованной ветке
  (решение 12.10.2026).
  Группы ревью: задачи со строкой `**Review group:**` ревьюятся одним ревьюером на группу (один
  пакет ревью от BASE перед первой задачей группы до HEAD после последней, строка `normal`-ревью
  таблицы моделей), исполнители по-прежнему по одному на задачу. Журнал переживает сжатие контекста:
  строка `Group G<n>: base <sha>`, `done, awaiting group G<n> review` по каждой задаче группы,
  правила продолжения с середины группы и с круга правок группы; задача группы остаётся в работе до
  приёмки, приёмка пишется по каждой задаче с её собственным диапазоном коммитов. Ревью группы не
  теряется: если следующая задача вне группы или задач не осталось, ревьюятся сделанные задачи
  группы. Предварительная проверка плана сверяет группы (только `normal`, подряд, 2–4), неверные
  делит или ревьюит по задачам; находку на несколько задач правит один исполнитель. Предел правок —
  3 круга вместо 5 и для группы, и для отдельной задачи: круги 1–2 — продолжить исполнителя, круг 3
  — новый исполнитель на более способной модели, дальше — прежний разбор открытых находок. Зачем: на
  этапе 5 Loveplace ревью каждой задачи с до пяти кругами правок обходилось около $8 на задачу,
  бэкенд этапа 6 с ревью только группами — около $2,1 без потери качества (решение 15.10.2026).
- `skills/subagent-driven-development/task-reviewer-prompt.md`: режим группы — несколько брифов и
  отчётов, один дифф; вердикт по спецификации на каждую задачу, по качеству — на весь дифф, каждая
  находка называет задачу (находка на несколько задач отмечает ту, чей код менять).
  `re-review-prompt.md`: для группы — брифы и отчёты задач, к которым относятся находки.
  `tests/claude-code/test-sdd-workspace.sh`: проверка, что `review-package` собирает коммиты всех
  задач группы (сам скрипт не менялся — диапазон BASE..HEAD уже это умеет). Зачем: ревьюер группы
  должен отвечать за каждую задачу, а исполнитель — получать свои находки.
- `skills/subagent-driven-development/re-review-prompt.md`: к выбору модели повторного ревью добавлено «сначала таблица моделей пользователя». Зачем: «дешёвый-средний уровень» не должен спорить с таблицей.
- `skills/writing-plans/SKILL.md`: в шаблоне задачи строка `**Risk:**` (уровни из правил
  пользователя, модели в плане не называются) и строка `**Review group:** G<n>`: подряд идущие
  задачи `normal` собираются в группы по 2–4, риски в группе не смешиваются, `complex` и `high`
  ревьюятся по одной, самопроверка плана проверяет группы; раздел `## Plan Review` — независимое
  ревью для плана больше пяти задач или с задачей `complex`/`high`, как ревью кода: правки находок,
  затем повторное ревью изменённых частей до чистого, не больше 3 кругов, оставшееся после третьего
  — строками `Ruling:` в итог для пользователя; ревьюер проверяет и группы; в
  `## Execution Handoff`, если инструкции пользователя задают способ исполнения, способ не предлагается на выбор:
  ссылка на план с кратким итогом и ожидание «да». Зачем: сессия не спрашивает про способ
  исполнения, который уже выбран, а ревью плана происходит до показа пользователю. Повторное ревью
  правок плана — потому что на этапе 5 ревью плана нашло 7 серьёзных находок, а их исправления никто
  не проверил (решение 15.10.2026).

Больше отличий нет. Каждое новое отличие — строкой в этот список.

## Установка

```bash
claude plugin marketplace add alkontv/superpowers
claude plugin install superpowers@alkontv-superpowers
```

## Обновление до новой версии автора

1. `git fetch upstream --tags` и найти новый тег `vX.Y.Z` (заметки — `RELEASE-NOTES.md`).
2. Посмотреть, что поменялось: `git diff <текущий тег> vX.Y.Z --stat`, затем построчно —
   особенно `hooks/`, `scripts/`, `index.js`, `package.json`, любые команды оболочки, сетевые
   запросы и инструкции агенту в `SKILL.md` (что он должен запускать, куда отправлять данные).
3. Влить тег в ветку `update/vX.Y.Z`, разрешить конфликты в своих правках, слить в `main`, запушить.
4. Плагин обновится сам при следующем запуске Claude Code; сразу — командами:

```bash
claude plugin marketplace update alkontv-superpowers
claude plugin update superpowers@alkontv-superpowers
```

Изменения скиллов подхватываются в новых сессиях.
