# Форк Superpowers (alkontv)

Плагин ставится отсюда, а не из официального маркетплейса Anthropic и не напрямую от автора:

- официальный маркетплейс отстаёт: 08.10.2026 он держал 6.4.1, а у автора с 25.09.2026 была 6.4.2
  с переписанным `writing-plans` (план без полного кода);
- изменения автора попадают в форк только после просмотра; сам плагин обновляется из форка
  автоматически (`autoUpdate: true` у маркетплейса `alkontv-superpowers`), поэтому в `main` форка —
  только проверенное;
- скиллы можно править под себя, и при обновлении автора правки не теряются.

## Что изменено относительно оригинала

- `.claude-plugin/marketplace.json`: имя маркетплейса `alkontv-superpowers` вместо `superpowers-dev`.
- Этот файл.
- Версия в `.claude-plugin/plugin.json` и `marketplace.json`: `<версия автора>-alkontv.N`. Без
  своего суффикса Claude Code не видит правок форка при той же версии автора и не обновляет
  плагин; N растёт с каждой правкой форка, при переходе на новую версию автора — снова 1.
- Политика проверок проекта главнее общих требований скиллов (`test-driven-development`,
  `subagent-driven-development/implementer-prompt.md`, `verification-before-completion`): если
  инструкции проекта задают объём проверок или принимают записанное доказательство на той же
  ревизии — следовать им, непрогнанное называть. Зачем: иначе скиллы требовали полный набор на
  каждую задачу и свежий прогон вопреки очереди тяжёлых прогонов, и модель выбирала между двумя
  противоречащими инструкциями сама. `writing-plans`: при передаче на исполнение предлагать свой
  шаблон исполнения пользователя, если он назван в его инструкциях; если пользователь уже велел довести
  работу до реализации — не спрашивать способ исполнения, а выбрать по его инструкциям и начать,
  останавливаясь только на продуктовых решениях. То же для `executing-plans` (объём проверок) и
  `finishing-a-development-branch` (полный набор — через механизм проекта: очередь или CI);
  `subagent-driven-development` — политика моделей пользователя главнее «cheapest tier».
- `skills/writing-plans/SKILL.md`: большой план (исполняется больше чем одной группой) пишется
  папкой — `README.md` (шапка, общие решения, таблица групп), `review.md` (только для ревьюеров),
  `tasks/NN-имя.md` (задача на файл); пункт самопроверки «Layout». Зачем: исполнитель группы
  получает общую часть и свои задачи, а не весь план; план удобно читать в Obsidian и на GitHub.
- `skills/brainstorming/SKILL.md`: раздел «When Your Human Partner Sets the Approval Boundary» —
  если пользователь сам задал, какие решения согласуются с ним (продуктовые и ключевые
  технические), и не читает спеки и планы, его граница заменяет одобрения всех трёх путей; ссылки
  на раздел — в HARD-GATE, в описании bounded, в «Anti-Pattern», в «Red Flags», на схеме, в
  чек-листе, в обзоре, на обеих развилках схемы и в «User Review Gate». В границе: пользователю —
  только открытые решения внутри неё, коротко (что получит пользователь, решения с рекомендацией,
  последствия), уже согласованное или заданное в поручении не переспрашивается; поручение сделать
  разрешает весь цикл без отдельного «да»; просьба только об исследовании или плане — выполнить её
  и остановиться; новое решение по ходу — пользователю, независимые части продолжаются. Зачем:
  поручение разрешает довести задачу до результата, а скилл требовал одобрять дизайн, спеку и план.
- `skills/writing-plans/SKILL.md`: шапка плана и передача на исполнение выбирают способ по правилам
  пользователя — этап по группам в его шаблон, небольшая задача не превращается в полный Workflow,
  план-папка только туда, где читают папки (`sdd-workspace` и `task-brief` ждут один файл); план
  пользователю на одобрение не отправляется, если он их не читает; передача останавливается на
  открытых решениях внутри границы пользователя — продуктовых и ключевых технических; если он
  просил только план — остановиться после него.
- `skills/executing-plans/SKILL.md`, `skills/subagent-driven-development/SKILL.md`: перед удалением
  рабочей папки плана файлы-доказательства проверки переносятся туда, где проект хранит логи, или
  папка остаётся. Зачем: папка не в git, и ссылки на доказательства в отчётах вели в пустоту.
  Там же среди поводов остановиться слияние, пуш и публикация больше не требуют вопроса, если
  правила пользователя их уже разрешают (слияние PR после зелёных проверок и итогового ревью).
- `skills/finishing-a-development-branch/SKILL.md`: если правила пользователя задают, как сдавать
  ветку, меню из трёх вариантов не показывается — сдать по правилам и доложить; удаление работы
  по-прежнему только по прямой просьбе.

Больше отличий нет. Каждое новое отличие — строкой в этот список.

## Установка

```bash
claude plugin marketplace add alkontv/superpowers
claude plugin install superpowers@alkontv-superpowers
```

## Обновление до новой версии автора

1. `git fetch upstream --tags` и найти новый тег `vX.Y.Z` (заметки — `RELEASE-NOTES.md`).
2. Посмотреть, что поменялось: `git diff <текущий тег> vX.Y.Z --stat`, затем построчно —
   особенно `hooks/`, `scripts/`, `index.js`, `package.json`, любые команды оболочки, сетевые
   запросы и инструкции агенту в `SKILL.md` (что он должен запускать, куда отправлять данные).
3. Влить тег в ветку `update/vX.Y.Z`, разрешить конфликты в своих правках, слить в `main`, запушить.
4. Плагин обновится сам при следующем запуске Claude Code; сразу — командами:

```bash
claude plugin marketplace update alkontv-superpowers
claude plugin update superpowers@alkontv-superpowers
```

Изменения скиллов подхватываются в новых сессиях.
